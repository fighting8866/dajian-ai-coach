# 长时答辩支持 V1：基线测量与瓶颈定位

## 为什么当前还不适合直接支撑约 9 分钟整段答辩

主链路目前是 **「整段录完 → 浏览器一次性上传音频/视频 → 后端（或 ascend_service）一次性分析」**，面向短时演示做了闭环验证。约 9 分钟的模拟答辩会带来：

- **上传体积**：WebM/压缩后仍可达数十 MB 级，受浏览器、反向代理、网络抖动影响大。  
- **单次分析耗时**：ASR / 视频解码与逐帧推理随时长近似线性或更差增长，易逼近 **HTTP / 网关超时**。  
- **单次失败代价**：任一步失败往往意味着 **整段重录或整段重传**，没有分段降级。  
- **结果稳定性**：长时音频的 VAD/转写误差累积、长时视频的检测帧统计方差，都会让 **audio_valid / vision_valid** 与指标波动更明显。

因此在未测清边界之前，**不应假设**「把演示时长拉到 9 分钟」仍能获得与 1～3 分钟相同的成功率。

---

## 当前链路的主要风险（整段模式）

| 环节 | 风险 |
|------|------|
| **whole file upload** | 体积大、弱网易失败；前端/网关 body 限制。 |
| **whole file analyze** | CPU/GPU/板侧算力长时间占用；内存峰值高。 |
| **timeout** | `ASCEND_*_TIMEOUT`、反向代理 `proxy_read_timeout`、浏览器等待上限。 |
| **单次失败代价高** | 无分段 checkpoint，失败即整段作废。 |

---

## 推荐演进路线（与比赛答辩叙事一致）

1. **第一步：基线测量与瓶颈定位（本次 V1）**  
   - 不改变训练主流程；通过 **日志 + 可选请求字段** 记录：blob 大小、各阶段耗时、`audio_valid` / `vision_valid`。  
   - 对比 **1 / 3 / 5 分钟**（再向目标 9 分钟外推）找出最先触顶的一环。  

2. **第二步：音频分段识别与合并**  
   - 将长录音切为多个 chunk 上传或流式处理；服务端合并转写与指标；降低单次失败半径。  

3. **第三步：视频分段 / 窗口分析与会话级汇总**  
   - 按时间窗口抽帧或分段上传；板侧或本地做窗口级指标，再在会话级做统计汇总。  

4. **第四步：9 分钟训练会话级展示**  
   - 前端进度、分段状态、可重试片段；与统一评分引擎约定「会话级」输入。  

---

## 第二阶段（V2）：会话级汇总与展示收口

### 为什么不能只看「单次片段」结果

长时答辩里，ASR 与视觉推理往往以 **分段 / 采样窗口** 为单位产出中间结果。若只展示「最后一次窗口」或「某一截转写」，会出现：

- **叙事断裂**：评委感知的是整场连贯表达，产品侧却只呈现局部文本或局部仪态比例。  
- **指标误读**：语速、停顿、正视比例等若在短窗上波动很大，容易与整场真实表现脱节。  
- **无法对齐评分**：统一评分引擎需要的是 **整场可解释输入**（合并转写 + 整场汇总的语言/视觉统计），而不是多个互不关联的片段 JSON。

因此需要在 **不改变训练主流程与对外主协议** 的前提下，把多段音频、多窗口视频的产出 **收口为同一会话的一份汇总**，并在 Result / Report 上明确标注「整场答辩」口径。

### 本会话汇总包含什么

| 维度 | 思路 |
|------|------|
| **Transcript** | 分段识别后合并为 `merged_transcript`（同时保留段计数、跳过/丢弃统计），整场阅读路径一致。 |
| **语言指标** | 在 ascend 侧标明 `audio_metrics_scope` 等为整场文件级汇总，避免与「单段」混淆。 |
| **视觉指标** | 在采样全视频路径上汇总 `forward_gaze_ratio` / `downward_head_ratio` / `posture_stability`，并记录 `processed_frames`、`skipped_frames`、`sampled_fps` 等，标明 `vision_metrics_scope`。 |
| **落库与 API** | `POST /session/stop` 将 `audio_session_summary` / `vision_session_summary` 写入 `metrics_bundle` 与结果；`GET /result`、`GET /report` 透传；前端 Result / Report 展示「长时会话摘要」。 |

### 与下一阶段「更真实模拟答辩 V1」的关系

第二阶段解决的是 **「整场有一份可信、可展示的汇总」**。再往后，要在 **时长与交互** 上更接近真实答辩（例如目标约 9 分钟、分段进度与可恢复上传），需要在当前会话级汇总之上，增强 **分段生命周期与前端反馈**，但 **评分与报告仍应读取同一会话级汇总对象**，避免回到「片段散落、无法对齐总评」的状态。

## 观测入口（实现于 V1）

| 位置 | 内容 |
|------|------|
| 后端 `POST /audio/analyze` | `[audio.analyze.baseline]`：`upload_bytes`、`analyze_elapsed_ms`、`audio_valid`、`transcript_len`、`provider` |
| 后端 `POST /vision/analyze` | `[vision.analyze.baseline]`：同上 + 三项视觉指标 |
| 后端 `POST /session/stop` | `[session.stop.baseline]`：客户端上报 blob 大小与分析耗时、`score_session` 耗时、**总 stop 耗时** |
| 前端 `Training.vue` stop | 控制台 `[stopSession.baseline]`：blob 大小、分析耗时、`session_stop_total_elapsed_ms` |
| `GET /api/system/provider-status` | `recommended_long_session_strategy`：`current_mode` / `next_stage_target` |

## 答辩时可如何表述

> 我们先用 **整段上传** 跑通闭环并固化开发板视觉链路；长时答辩场景下，瓶颈主要来自 **整段体积与单次推理耗时**。V1 通过 **基线日志** 量化边界；随后通过 **分段音频与窗口化视频** 降低单次失败半径，并在 **V2 第二阶段** 将会话级转写与指标 **汇总落库、在结果页与报告页统一展示**；再向 **更真实模拟答辩 V1**（约 9 分钟与分段交互）演进时，仍保持 **同一会话一份汇总** 的对外叙事。
